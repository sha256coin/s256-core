S256 LWMA Fork Transition Rehearsal

Run 2026-09-02 · local, isolated regtest · scaled-down rehearsal of mainnet's real height-17,500 AuxPoW/LWMA hard fork
Why this test: S256 mainnet is currently at block ~16,883 — roughly 600 blocks (~8–9 days) away from its real AuxPoW+LWMA activation at height 17,500. This rehearsal exercises the exact same code path (chain identity, activation gating, and LwmaCalculateNextWorkRequired) on an isolated local chain, scaled down to a tractable size, to check the transition and LWMA's hashrate-adaptation behavior before it happens for real.

Scenario

Three simulated miners mine from genesis. The classic-DAA-to-LWMA fork is scaled from mainnet's real height 17,500 down to height 96 — the smallest fork height at which LWMA's own N=96-block window has a full, real, pre-fork-timestamped history immediately available, exactly mirroring mainnet's actual situation (mainnet's height at its fork is already far past 96). Reading the result

  • Fork transition (height 96): clean, no crash, no stall, no consensus error. LWMA's own bootstrap guard (height < N in LwmaCalculateNextWorkRequired) means the block at the activation height itself still uses the pre-fork floor, and real per-block computation starts one block later (97) — a minor off-by-one against the naive "N=96 ⇒ active at 96" assumption, not a bug.
  • Baseline, 3 miners (97→155): steady, monotonic tightening. The simulated 3-miner pace was faster than the network's target spacing, and LWMA correctly raised difficulty in response, block after block.
  • Drop to 2 miners (156→~172): difficulty keeps rising for about 15 more blocks before turning — expected lag for a weighted moving average still dominated by the faster 3-miner blocks still inside its window.
  • Drop to 2 miners (~172→~194): difficulty eases, as LWMA's window fills with the slower post-drop blocks.
  • Drop to 2 miners (~194→206): a partial re-tightening before the phase ends — the window is still catching up to the new pace when phase 4 begins. This wobble is real LWMA behavior (not test noise): a 96-block weighted average doesn't snap to a step change in hashrate, it converges toward it, and 50 blocks wasn't quite enough to fully settle.
  • Recovery, 3 miners again (206→255): steady, monotonic tightening resumes immediately and continues cleanly for the full 50-block phase — no stall, no oscillation this time (starting from an already-partially-adjusted state rather than a fresh step change).
Bottom line: LWMA activates cleanly at the fork, degrades gracefully (with expected lag, not runaway instability) when hashrate drops, and recovers cleanly when it returns. 255 blocks, zero crashes, zero stalled/rejected blocks, zero consensus errors.

Methodology & how this was actually run

First attempt used real competitive CPU mining (3 concurrent generatetoaddress processes racing on testnet) through a live, wall-clock pre-fork phase. That surfaced something worth recording: mining pre-fork blocks in ~4–5 real seconds each (instead of the real 1200s target) made LWMA see an "impossibly fast" historical window the instant it activated, and it responded exactly as designed — by spiking the required difficulty roughly 250×, past what 3 CPU threads could plausibly solve in reasonable time. That's correct LWMA behavior, but it's an artifact of compressing the test's own timeline, not something that would happen on mainnet (whose real pre-fork blocks are already paced at the real ~20-minute target).

This run switched to regtest with a temporary consensus test-patch (fPowNoRetargeting=false, activation heights set to 96 — regtest normally disables retargeting entirely, and this rehearsal needed it enabled) and used setmocktime (regtest-only) to give each block a controlled, phase-appropriate timestamp — 1200s/block pre-fork and at baseline-equivalent pace, 400s/block for the two "3 miners" phases, 600s/block for the "2 miners" phase — while every block's proof-of-work was still genuinely solved and validated through real RPC calls (generatetoaddress, real block acceptance, real LwmaCalculateNextWorkRequired execution) rather than a unit-test mock. The test-only patch is local to this rehearsal and is not part of any real chain's consensus rules.

The one-time large jump at height 72 in the overview chart is the classic DAA's own interval-boundary retarget (regtest's nPowTargetTimespan/nPowTargetSpacing gives a 72-block interval) — expected, pre-existing, unmodified behavior, unrelated to the LWMA fork itself.

Related evidence

Separately, this build's daemon completed a full real sync of the live S256 mainnet chain (genesis through height 16,883, against real network peers) with zero errors, warnings, or reorgs — confirming the consensus code is sound on the real chain right up to (but not yet through) the real fork. This rehearsal is the complementary piece: what happens at and after the fork, which the real chain hasn't reached yet.
